# 电影创作交互 · 已确认决定

**确认日期：** 2026-09-05

**依据：** 所有者逐轮确认的提案、剧本、视觉、试拍、调度、annotation 与声音决定；包含成片后台词、语气和角色声线修改及必要局部补拍。

**状态：** 创作交互原则已确认，页面与关键操作见[前端规格](frontend-spec.md)。独立分支已实现可点击原型，用户体验审阅待完成；电影运行能力仍待实现和真实验证。

## 1. 适用背景

- 当前目标是 90–120 秒 AIGC 科幻电影。
- 面向 AIGC 零基础用户，以自然语言和多轮对话明确意图，无需提供素材。
- 默认共创，支持明确授权的托管与部分托管；同一项目可以切换模式。
- 用户通过故事与视听表达判断是否愿意继续创作。正式剧本质量评测属于产品评测；运行时可以给创作意见或进行一轮专项审查，但不引入自动评分、否决和反复改稿循环。

以上为承接此次结构的既有决定；早期报告中的 60–90 秒、默认全自动等表述已过时。

## 2. 右侧故事提案

提案是一份可阅读、可修改的简短故事文档，包含三个内容区。

| 内容区 | 必须表达的信息 | 用户的判断 |
|---|---|---|
| 片名与一句话故事 | 暂定片名；核心处境、事件或人物行动。已知时长等要求简短显示。 | 我会看到一个什么故事？ |
| 完整故事 | 人物、必要的科幻设定、事件发展、结果；按影片计划呈现的顺序叙述，人物情绪通过行动、选择和结果体现。 | 故事是否有趣、可信，结尾是否值得拍？ |
| 准备怎样拍 | 视觉方向、声音方向、节奏，以及这些选择如何服务当前故事。 | 是否符合我期待的观看感受？ |

完整故事占主要篇幅。正文初始建议约 300–500 个中文字，随故事调整；这是呈现目标，不是字数门槛，也不能据此推算成片时长。

人物与必要设定默认融入正文。只有理解确有困难时，才单独展开简短人物关系或设定说明。首次提案不要求完整人物小传、世界观百科或镜头技术参数。

固定的是信息覆盖，叙事结构由故事决定。支持倒叙、群像、开放结局、安静的情绪表达等。开放结局仍需说明最后呈现的事件或画面，以及刻意保留的疑问。

“准备怎样拍”应给出具体选择及其作用。例如局部暖光怎样表现人物、环境声音何时占主导、某个动作为何需要停留。“史诗级、震撼、电影感”等形容词不能独自构成视听方向。

## 3. 主导演创作讨论

Agent 的创作意见放在对话中，包含：

1. 理解了用户哪些意图；关键情节由 Agent 补充时，应说明其来源。
2. 为什么推荐当前方案；可以指出具体创作机会和实际顾虑。
3. 当前最值得讨论的一件事，优先围绕会明显改变影片方向的选择。

用户不需要先填写专业制作表格。已有信息继续复用；同一问题不重复询问。

创作意见帮助用户决策，不构成自动剧本评估门禁。

## 4. 向后续制作承接

- 用户认可故事后，正式剧本展开具体场景、动作与对白。
- 提案中的人物身份、关键设定、情节结果和视听方向，成为后续生成依据。
- 共创与托管使用同一提案结构；是否等待审核遵循当前授权范围。
- 文档允许手动修改。修改文档本身不自动触发相关素材和视频调整；用户明确要求应用修改后，再按已确认的修改流程执行。
- 首次提案结构不增加分镜审批、费用上限或新的自动评分要求。

## 5. 正式剧本结构 · 已确认

故事提案通过后，正式剧本按场景组织，作为用户审核的依据。每场按内容需要写清：

| 内容 | 展开程度 |
|---|---|
| 地点与时间 | 故事发生在哪里，是否有时间变化。 |
| 画面与动作 | 观众实际看到什么，人物做什么。 |
| 对白与关键声音 | 人物说什么，以及影响剧情或情绪的声音。 |

用户在右侧逐场阅读、手动修改。具体镜头拆分和生成提示词由后续制作规划展开。并非每场都必须有对白；场景内容依剧本需要确定。

手动修改与应用修改的关系继续遵循第 4 节，不因采用分场结构而自动触发生成。

## 6. 代表性试拍 · 已确认

共创模式默认在批量生成视频前安排代表性试拍，允许用户跳过审核或授权托管。

- 剧本和关键视觉方向确认后，从实际剧情中选择代表性片段。
- 生成动态画面并配上关键声音，让用户感受人物表演、动作、质感与声音配合。
- 用户认可后继续制作；在跳过审核或托管时，按当前授权继续。
- 合适的试拍素材直接用于成片。
- 片段长度与内容按剧本决定，不固定为某类镜头。

试拍的目的，是尽早发现文字与参考图获得认可后，动态声画仍与用户期待不符的问题。它会增加前置等待，对首次完整成片时间和成本的影响尚待实测；本次决定不设额外费用上限。

## 7. 按需对比试拍 · 已确认

当用户对试拍不满意，且语言沟通仍无法明确修改方向时，Agent 可以提议一次局部对比试拍：

- 以同一小段剧情为基础，提出两个有明确差异的拍摄版本。
- 先解释差异，经用户确认后生成，让用户通过观看表达偏好。
- 继续遵循“理解、给意见、用户确认后执行”的修改流程。
- 仅在有必要时使用，不作为每轮修改的固定步骤。

对比试拍会增加生成成本和等待。该能力的确认不构成默认反复生成候选的授权，也不设新的硬性费用上限。

## 8. 运行中修改的决策分工 · 已确认

具体调度由模型结合用户意图、剧情、制作状态和当前授权判断。程序提供可靠的执行能力和状态校验。

模型负责判断用户在讨论可能性还是明确要求修改、改动影响哪些内容、何时暂停或继续、哪些素材可以复用，以及需要向用户解释什么。

程序需要提供：

- 制作期间接收新消息，并在明确的执行边界交给 Agent 处理。
- 查询任务状态、取消未开始的任务、尝试取消运行中的任务，并返回真实结果。
- 记录素材所属计划版本，避免旧任务的迟到结果直接覆盖用户已确认的新版本。
- 可靠执行明确停止指令和当前共创／托管授权；手动改稿不自动触发生成。

“相关任务暂停、无关任务继续”的固定默认流程建议已撤回。它可以成为模型选择的处理方式，但不枚举并固化所有修改情形。停止请求不等于外部生成已经成功取消。

本节定义能力与行为边界，不决定采用何种队列、框架或中断实现。已核对的参考项目也未证明完整具备上述实时选择性调度能力。

## 9. 首轮视觉审核的呈现 · 已确认

主要人物和核心场景需要用户确认，等待方式遵循当前共创／托管授权。首轮视觉审核主要展示一组来自实际剧情的电影画面草案。

- 将关键人物放进对应场景，帮助用户一起判断人物外观、服装、环境、光线和整体气质。
- 画面数量和选择由 Agent 按剧本决定。
- 制作需要的角色三视图、道具细节等由 Agent 按需准备，用户可以展开查看。
- 需要单独确认的细节，由 Agent 拿出来讨论。
- 视觉方向获得认可后，进入动态试拍；是否等待用户依当前授权处理。

上述为审核呈现方式，不要求所有制作资产采用同一种生成顺序，也不改变共享参考资产、按镜头选择生成方式的方向。

## 10. 视频时间点标注 · 已确认

采用所有者描述的 Codex annotation 交互作为产品参考：用户在视频时间点写标注，标注自动回到对话输入框；输入框承载多条标注，支持单条提交，也支持积累多条后统一提交处理。此处记录所有者指定的交互，不声称已核对 Codex 的内部实现。

- 每条标注包含所引用的视频、时间点及用户意见。
- 标注自动加入待发送的对话内容，加入标注本身不发送消息，也不启动生成。
- 用户可逐条提交，或整理多条标注后一起发送；对话仍可附加整体修改要求。
- 为保持定位可靠，标注关联创建时的视频版本。视频后续变化不应使旧标注静默指向另一处内容。
- Agent 结合视频上下文和本次提交的意见判断修改范围，沿用现有共创／托管的执行方式。
- 标注时间点是理解意见的依据，不把实际修改强制限定在一个时间点或一个镜头内。

本方案替代此前待讨论的单独“修改这里”入口建议。界面仍围绕对话与视频预览，不引入专门的视频剪辑工作台。

## 11. 声音试听与反馈 · 已确认

声音审核放进已有的试拍和成片预览，用户结合画面判断对白、配乐和音效是否合适，不额外增加一轮固定的声音审核。

- 默认结合画面试听；用户想挑声线、比较配乐或听清某个音效时，按需单独试听。
- 相应声音素材在对话或侧栏中播放。可独立试听、替换的范围必须与实际保留的音轨对应，不能把已混合声音假定为独立音轨。
- 声音反馈沿用 annotation，可标注音乐音量、对白语气等问题。
- 用户也可直接在对话中提出整片声音方向的调整。
- 修改继续遵循既有共创／托管和模型判断影响范围的原则。

## 12. 成片后的配音修改 · 已确认

MVP 支持成片后修改台词、语气和角色声线，并允许按需局部补拍。

- 用户可以通过 annotation 或自然语言提出修改，例如改一句台词及其语气。
- Agent 判断实现方式：能独立调整声音时处理声音；涉及口型、表演或时长变化时，可能需要连带修改相关镜头。
- Agent 先说明修改方案，再按既有共创／托管授权执行。
- 具体影响范围由模型判断，不固定要求每次配音修改都重生成视频。
- 本次确认产品能力范围，声音独立编辑、口型处理及局部补拍效果仍需真实验证。

## 13. 已确认原则之外的待办

不逐项枚举模型处理每一种创作情况的规则。前端三栏、产物标签、编辑与审核、主题、Windows 本地部署等方向已确认，交互体验进入已授权的原型制作与审阅。消息交付、任务控制、版本校验、实际音轨能力和生成质量在后续接入与真实验证中落实。

具体待办见[技术评审基线](../architecture/technical-baseline.md)，不因本轮功能确认而视为已定案或已验证。
