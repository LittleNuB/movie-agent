# 前端呈现与交互 · 原型已授权

**日期：** 2026-09-06

**状态：** 核心交互、三栏结构、A 日间／B 夜间、Windows 本地个人部署与模型密钥设置已确认。独立分支已实现可点击原型，具体布局和操作体验仍待用户审阅；未完成真实电影能力验收。实际交付见[原型任务](../plans/clickable-prototype.md)。

## 1. 沿用的已确认决定

- 面向 AIGC 零基础用户，以自然语言和多轮对话开始，无需提供素材。
- 对话为主，右侧承载可编辑剧本、图片、视频及必要声音素材。
- 共创与托管使用同一项目和产物，显示真实进展与关键审核内容。
- 手动保存剧本不触发媒体调整；明确要求应用修改后，Agent 理解、提出方案，按授权执行。
- 视频时间点 annotation 回到输入框，支持单条或多条提交；添加不等于发送。
- 支持版本比较与恢复、素材查看和下载；不做多轨时间线编辑器或专门的视频工作台。

这些决定不自动确定导航、组件布局、切换行为或视觉风格。具体语义仍以[产品基线](product-spec.md)和[交互决定](creative-interaction.md)为准。

### 1.1 右侧作品组织与多标签页 · 已确认

所有者于 2026-09-06 接受以下呈现方式：

- 右侧保留轻量的作品导航，用户可从这里找到剧本、视觉方案和影片等产物。
- 选择产物后，在右侧作品区域打开对应内容。
- 对话中的产物卡片也能直接打开对应内容，查找作品不依赖翻阅聊天记录。

同日后续，所有者提出采用与 Codex 类似的右侧栏，支持收起、打开及多开。依此调整呈现方向，不将此前“同一个主预览区域”的表述作为限制多开的依据。

所有者随后明确：不需要并排可见，像浏览器一样切换即可。采用可展开、收起的右侧栏；剧本、图片、影片等可分别打开为多个标签页，每次显示一个标签页的内容，不增加并排或分屏显示要求。

当前记录的是所有者描述的交互参考，不声称已核对或将完整复制 Codex 的界面与实现。作品导航用于查找产物，标签页用于切换已打开内容；具体导航分组和布局继续讨论。版本查看与恢复入口见第 1.8 节，比较时遵循本轮单个内容可见的选择。

### 1.2 新产物的默认打开行为 · 已确认

所有者接受以下默认行为：

- 首次生成产物时，自动展开右侧栏并展示，帮助初次使用者发现产物。
- 用户正在查看其他内容，或已主动收起侧栏时，通过对话卡片提示新产物，保留当前界面状态。主动查看或收起的选择优先于首次自动展示。
- 用户点击产物卡片，或在对话中明确要求查看时，打开对应标签页。

这一定义控制产物如何呈现，不改变共创／托管的授权范围与审核要求。标签页排序、重复打开、切换后的阅读和播放状态等具体细节尚未在本轮冻结。

### 1.3 制作过程的信息呈现 · 已确认

所有者接受“主导演统一沟通＋可展开的制作进展”：

- 主导演在对话中说明当前工作、遇到的问题和需要用户判断的事项。
- 制作进展呈现真实状态，并提供相关产物入口，例如画面已生成、环境声正在制作；这些是示例，不规定固定制作顺序。
- 专业 Agent 的任务、执行结果与重试情况作为可展开的执行细节，默认折叠。
- 重要进展、问题和审核请求直接呈现在对话中；需要审核时，明确列出待审内容与查看入口。

此决定沿用共创与托管均展示真实进展的原则。具体进展组件、更新方式及失败恢复操作仍需细化，不把界面上的工作描述作为强制执行阶段。

### 1.4 首次进入与新建影片 · 已确认

所有者接受以表达想法为核心的首屏：

- 页面中央提供输入框，提示“你想拍一个怎样的故事？一句话、一个画面，或一种感受都可以。”
- 输入框下方提供少量灵感示例；点击后填入输入框，用户可修改，再主动发送。
- 发送第一条消息后自动建立影片项目，进入共创对话；项目名称可随故事形成后再修改。
- 右侧作品栏初始收起，首个产物出现时遵循第 1.2 节的默认打开行为。

本轮确认首次进入与开始创作的方式；已有影片的入口见第 1.5 节。示例帮助用户开始表达，不作为固定故事模板或自动提交指令。

### 1.5 影片项目导航与页面结构 · 已确认

所有者接受左侧可收起的影片项目列表：

- 顶部提供“新建影片”入口，进入第 1.4 节的开始创作流程。
- 项目按最近活动排列，显示片名与简短状态，例如“制作中”“待审核”；状态以实际项目情况为依据。
- 点击项目，回到对应的对话与作品。
- 同一部影片的修改和历史版本保留在该项目内部。

主页面结构为“左侧选影片、中间对话、右侧查看和编辑作品”，两侧均可收起。左侧项目列表与右侧项目内作品导航承担不同的查找任务。

切换项目后的后台制作行为已在 1.14 确认；跨项目任务的并发容量与调度机制仍待技术实现确定，切换项目本身不增加制作授权。

### 1.6 共创与托管的模式入口 · 已确认

所有者接受在输入框旁保留模式控件：

- 默认显示“共创”，点开可了解含义并切换。
- 托管时显示“托管”，可查看当前授权范围。
- 部分托管显示简短摘要，例如“共创 · 声音已托管”。
- 用户也可在对话中调整模式与授权范围，控件同步反映实际生效的状态。

模式控件服务于当前影片项目，沿用已有的共创、托管和部分托管语义；界面文案与实际授权保持一致。

### 1.7 剧本编辑与提交 · 已确认

所有者接受“自动保存草稿＋明确提交修改”：

- 编辑剧本时自动保存，保存成功后显示“已保存”；存在尚未提交的改稿时，提示“有修改未提交”。
- 用户点击“提交修改”，将当前改稿交给主导演理解和处理；也可直接在对话中要求应用改稿。
- 后续沿用既有模式：共创时，主导演先说明修改方案，再由用户确认；托管时，按当前授权范围推进。
- 保存文字本身不触发媒体调整，编辑中的草稿与已用于制作的剧本保持可区分。

这一定义明确了前端的保存与提交操作，不改变用户手改保护、批准绑定版本和过时结果不能覆盖新稿的既有要求。

### 1.8 版本查看与恢复 · 已确认

所有者接受“历史版本单独打开查看，明确选择后再从它继续”：

- 作品内提供“历史版本”入口，每个版本显示时间和主要改动，例如“调整结尾”“更换配乐”。
- 历史版本打开为独立标签页，用户通过切换标签比较内容，沿用每次显示一个内容的呈现方式。
- 界面明确标识正在查看的版本及当前采用的版本，浏览历史版本不改变当前作品。
- 用户需要退回旧版时，点击“从此版本继续”；已有版本与未提交的手改草稿保留。

查看、采用和继续修改的状态应保持可区分。未提交草稿的保留继续遵循手改保护要求，不能在采用历史版本时被静默覆盖。

### 1.9 对话内审核卡 · 已确认

所有者接受用简洁的对话内审核卡承载既定关键节点的确认，包含：

- 待审内容、对应版本及打开作品的入口。
- 主导演的建议，说明本轮主要需要用户判断什么。
- 确认后的下一步，例如继续制作其余镜头；具体内容取决于当前方案。
- “确认并继续”按钮；有修改意见时，用户可直接在对话中提出。

自然语言回复同样可以完成确认，按钮和文字回复对应同一轮具体内容。托管中已授权跳过的审核继续遵循原规则；审核卡不增加新的固定审核节点，也不改变当前内容与批准范围绑定的要求。

### 1.10 输入框中的标注卡片 · 已确认

所有者接受以可编辑的标注卡片整理时间点反馈：

- 每条卡片显示所引用的视频版本、时间点和用户意见。
- 发送前可以编辑或移除卡片；点击时间点，可回到对应视频版本的位置查看。
- 多条卡片集中在输入框中，仍可在下方补充整体修改要求。
- 沿用单条或批量提交方式，卡片进入输入框时保持待发送状态。

卡片的引用继续绑定创建标注时的视频与版本。此处确认反馈草稿的呈现和整理操作，不将时间点当作固定修改范围；提交后的理解、方案和执行遵循既有共创／托管流程。

### 1.11 首版设备范围 · 已确认

所有者接受首版以电脑浏览器为完整创作入口，以笔记本和台式机为主要使用场景。三栏布局、剧本编辑和视频时间点标注围绕键鼠及较大的屏幕设计。

手机端完整创作适配延后，不作为本轮 MVP 的必需交付。所有者进一步确认首版正式支持 Windows，macOS／Linux 后续适配；已确认的本地个人部署与模型密钥配置见 1.16，安装分发及参赛交付方式仍需确定。

### 1.12 日间与夜间视觉方向 · 已确认

所有者查看内置 imagegen 生成的三方案视觉参考后，总体认可效果，并明确选择：

| 参考方案 | 采用方式 |
|---|---|
| A：浅色 | 作为日间主题，以中性浅色界面及蓝色强调为参考 |
| B：深色 | 作为夜间主题，以深灰界面及暖色强调为参考 |
| C：明暗分区 | 不采用 |

两种主题沿用已确认的布局与交互，以配色和视觉样式区分。此次认可的是总体方向，具体色值、字级、间距和各操作状态仍需在实际原型中调整。

所有者进一步确认：主题默认跟随系统，支持用户手动切换并记住选择。手动偏好生效时按用户选择显示，也应能重新选择跟随系统；具体入口位置和控件样式留待原型细化。

原始[三方案视觉参考图](../assets/frontend-theme-comparison-2026-09-06.png)已原样保存到工作区，C 仅作为已否决候选保留在对照图中。该图是静态视觉示意，影片、项目名称和界面内容均为示例，不是可运行前端或真实生成影片的验收证据。

生成工具为内置 imagegen。生成要求为：在同一试拍审核与标注场景中保留一致的项目导航、主导演对话、模式入口、审核卡、标注卡、多标签作品侧栏和科幻电影预览，分别比较浅色、深色与明暗分区；完整生成请求保留在本任务会话中。此处为要求摘要，不是逐字提示词。

### 1.13 制作中的消息与中止入口 · 已确认

所有者接受“消息随时可发，停止制作使用独立按钮”，并以自己描述的 GPT 中止体验作为交互参考：

- 制作期间输入框保持可用，用户可随时向主导演发送消息。
- 输入框旁提供独立的“停止制作”按钮，作用于当前影片任务。
- 点击后及时反馈，依据实际执行状态显示“正在停止”或“已停止”，不把发出停止请求直接当作全部工作已结束。
- 中止后保留对话、草稿和已完成的作品。

新消息对当前制作的影响仍由主导演结合内容与授权判断。此处确认产品交互，不据此推断 GPT 的内部实现，也不承诺外部生成服务能够即时取消任务；实际任务状态与结果处理须在实现时落实。

### 1.14 离开页面与返回制作 · 已确认

所有者接受：后端服务仍在运行时，切换项目、刷新或关闭页面，不自动中止已授权的制作。

- 已授权的制作可在后台继续，仍遵循当前共创／托管范围。
- 遇到需要用户审核的节点时等待用户，不因页面关闭而跳过审核。
- 返回项目后显示实际进度及已有产物，不因页面重新打开而重新提交生成任务。
- 停止制作由明确的中止操作触发；离开页面本身不视为中止或新增授权。

此处确认页面生命周期与制作任务的关系，不承诺后端停机时仍能制作。本地个人部署方式见 1.16；服务生命周期、跨项目并发容量和服务重启后的恢复机制仍需技术设计与验证。

### 1.15 异常说明与恢复沟通 · 已确认

所有者指出，异常说明可以像正常 Agent 一样直接输出文字，没有必要强制使用卡片。此前提出的专用异常卡片与对应操作按钮方案撤回。

主导演通过正常对话说明遇到的问题、实际已知的原因、保留的成果和建议的后续处理，用户可直接回复意见或继续指令。说明内容依具体问题组织，不要求每次填满固定模板。需要查看相关作品时可附上作品链接。

恢复处理沿用已有的共创／托管授权与模型判断原则；本节确定沟通形式，不新增自动重试次数或固定恢复流程。

### 1.16 本地个人部署与模型密钥配置 · 已确认

所有者提出像 Pi Agent 和 DeepSeek Harness（DSH）一样，作为本地 Agent 供个人部署，并接受首版由用户自行准备模型 API Key，产品提供设置页引导填写与检查连接。此前助手提出的受邀用户共用一个服务、按用户隔离项目的方案未获确认，不作为首版默认范围。

采用个人电脑运行 Agent、后台任务管理与项目存储，浏览器打开本机创作界面的形态。既有三栏、多标签作品、共创／托管等交互沿用。模型推理和媒体生成调用用户配置且已适配的 API；本地保存项目不表示提示词和必要参考素材不发送给模型服务。此部署方向不要求改用 Pi 或 DSH 作为底层框架，AgentScope 首选路线保持不变，具体接入仍待验证。

设置页负责引导用户配置所需模型凭据，并明确呈现连接检查的实际结果；检查通过不直接等同于全部模型能力或影片质量已验证。具体检查请求、凭据保存机制和界面布局留待实施设计。本轮确认的是产品配置体验，不触发新的 API 检查或媒体生成。

关闭浏览器但本地服务仍运行时，沿用 1.14 的后台制作行为。电脑关机、休眠或本地服务停止时，本地调度不能继续；已经提交的云端生成是否仍在执行须查询实际服务状态，恢复后应核对已有任务与结果，避免重复提交。该恢复能力尚未实现或验证。

以下为 2026-09-06 本轮核对的官方依据，仅支持部署方式的可行性，不构成本产品的集成验收：

- [DSH 官方 README](https://github.com/deepseek-ai/deepseek-harness)：提供本地 Web 服务启动方式，默认使用回环地址并打开浏览器。
- [Pi 官方 README](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/README.md)：提供本地 CLI、RPC 和 SDK 使用方式；旧仓库地址在本轮访问时重定向到此处。
- [AgentScope 官方 README](https://github.com/agentscope-ai/agentscope)：提供 Python SDK，以及在本机分别启动服务端和 Web UI 的示例。

所有者已确认首版以 Windows 为正式支持与验收平台，macOS／Linux 后续适配。具体 Windows 版本和硬件要求需依据安装、运行与媒体合成验证确定，不从浏览器可打开界面推断后端已支持其他操作系统。

安装与启动的分发方式仍需确定。此处记录已确认的部署与配置方向，不代表已经交付安装包或已决定采用参考项目的启动命令。

### 1.17 用户自定义 API 与模型 · 2026-09-06 修正

所有者审阅原型后指出：此前模型选择属于自己的使用配置，不应预设在完整产品里。设置改为“服务连接”和“用途分配”：用户填写名称、接口类型、Base URL、API Key，获取或手动添加模型 ID，再选择各项创作能力使用哪个模型。支持多个连接、一个连接多个模型；初始连接与模型为空。

旧原型的四个固定模型栏位已被替代。新表单可编辑，API Key 默认遮罩；原型仍无真实请求，Key 仅在页面内存暂存，配置与模型清单可以保存。模型能力、专用协议和实际凭据保存另行验证，详见[完整设置规格](model-settings.md)及 [ADR 0004](../adr/0004-user-configured-models.md)。

## 3. 前端复用边界

以 ViMax 作为电影领域代码起点不包含原样复用其前端的决定。吸收 AdCraft 或 OpenMontage 的能力也不代表采用其整套界面。当前没有选定任何开源项目的前端作为最终产品界面。

后续先定义页面与交互，再评审哪些现有组件、样式或代码值得复用；整体复用、局部复用或重新实现均未定案，不把“复用开源项目”或“全部重写”当成默认产品结论。
