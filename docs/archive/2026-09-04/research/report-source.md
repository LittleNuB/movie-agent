# 从视频后期 Agent 到科幻电影导演 Agent：调研综合底稿

**受众：** 项目所有者与后续产品、工程协作者
**日期：** 2026-09-04
**状态：** 调研综合候选，不是已批准的 DESIGN、ADR 或实施票据
**决策期限：** 2026-09-14 作品提交截止前

## 所有者校正 · 2026-09-04

用户接受 60–90 秒；否决单主角、单空间、单异常作为产品范围。该组合仅是一个低复杂度测试用例。产品是科幻电影 Agent，不绑定一种剧本类型。其他复杂度、风格、镜头数、自动化、架构及模型建议尚未获得批准。

## 研究范围与假设

本轮调研回答五个问题：现有项目是否适合参加 AI+∞ 开发者创作大赛电影 Agent 赛道；参赛版应解决什么用户问题；怎样把科幻电影制作知识变成 Agent 的可执行合同；哪些现有代码值得复用；在约十天内什么技术路线最有机会形成可运行、可复现、能生成完整短片的作品。

默认面向个人参赛者和评审，不假设团队、既有 DGX Spark 资格、付费模型余额或可公开全部私有仓库。交付格式采用中文 Markdown，方便进入仓库继续讨论和版本化。研究只做资料与代码检查，没有调用付费生成模型、生成参赛媒体、创建账号、部署、发布或提交。

## 直接结论

项目适合参赛，但当前 v0.4 不能直接作为电影 Agent 提交。最佳路线是建立一个并行的 v0.5「科幻电影导演 Agent」领域层：用户输入一句科幻构想，系统在默认全自动模式下完成故事、视觉圣经、镜头计划、素材生成、粗剪、整片审查、定向修复、声音与交付，目标成片 60–90 秒，并展示可追溯的多 Agent Harness。

建议保留现有持久状态、不可变版本、恢复、素材身份、ProviderAttempt、成本记录、Remotion/FFmpeg、ReviewPacket、QC 和项目包；冻结旧口播模板合同，不再把 `PrimaryVideo → Template → FirstCut` 强行扩展为从零造电影。新系统建立 `FilmBrief → StoryBlueprint → WorldBible → ScenePlan → ShotPlan → Candidate → PictureLock → SoundPlan → FilmVersion`，通过适配器复用旧基础设施。

首发生成路径建议使用 MiniMax H3 API 的 768P 多参考视频音频生成，Wan2.2 TI2V-5B 作为可选本地开放回退。公共魔搭创空间承载控制面、状态、预览与轻量合成；重模型通过 API 或独立 GPU Worker 运行。公开 Studio 禁止启用当前具有用户权限的 Pi Shell；Pi 只保留在可信本地创作/修复模式。

不建议为了“看起来像多 Agent”迁移到全新的 Python 框架。现有 TypeScript 运行时的持久性比许多直接竞品更成熟。应借鉴 LangGraph/AgentScope 的显式图、分工、追踪和有界回路，但维持一个状态真相源。

## 比赛合同

截至 2026-09-04，电影 Agent 评分为：多 Agent Harness 架构与工程实现 30 分；统一一句话生成测试 25 分；技术创新与模型工程 25 分；自主作品质量 10 分；复现、开源与部署 10 分。作品报名截止 9 月 14 日 12:00，提交截止当日 22:00。Agent 需部署到魔搭创空间并提交创作手记；比赛整体要求一部 1–5 分钟原创科幻视频、AI 生成标识、素材与肖像权合规、评审期间链接可访问。来源：[比赛官网](https://modelscope.cn/active/AIstudio)。

这意味着系统必须同时证明四件事：一句话输入可以走通；多 Agent 角色有真实责任；系统能在失败后继续而非只展示理想流程图；最终短片的叙事、声画和剪辑达到可观看水平。

## 外部方案带来的核心证据

FilmAgent 证明导演、编剧、演员和摄影角色通过 Critique-Correct-Verify 可以改善剧本与镜头选择，但其 Unity 环境和动作空间预先受限，不能直接作为开放生成系统。[FilmAgent](https://arxiv.org/abs/2501.12909)

MovieAgent 建立了脚本—场景—镜头的分层规划，但公开代码仍要求用户准备脚本、人物照片/声音和部分定制权重，离一句话、低门槛、稳定部署仍有距离。[MovieAgent](https://arxiv.org/abs/2503.07314)

MAViS 的可用价值在于把生成模型限制写回剧本合同：每个镜头只承担一个简单动作，避免细小文字和复杂连续动作，用手、背影、环境与关键道具特写承担转场，并让结构、内容、风格审查先于生成。其 3E 循环能提高成功率，但完整论文流水线平均耗时和算力很高，不能照搬。[MAViS](https://aclanthology.org/2026.eacl-long.101/)

FilMaster 与本项目根因高度吻合：单纯按镜头让 LLM 想象摄影会得到模板化、缺乏节奏的结果；更有效的方法是用场景叙事目标检索抽象镜头语言，先形成粗剪，再由观众视角审查，最后做结构、时长与多尺度声音精剪，并输出 OTIO。[FilMaster](https://arxiv.org/html/2506.18899)

Hollywood Town 的消融显示，层级编排主要改善叙事结构与节奏，按需上下文和有界回路进一步改善声画表达与吸引力。不过其测试只有三个提示和四位专家，适合作为设计线索，不适合当作普遍定律。[Hollywood Town](https://arxiv.org/abs/2510.22431)

FilmBench 指出当前模型普遍更擅长静态清晰度与灯光，薄弱项集中在动作表演、镜头运动吸引力、人物运动真实性、情绪表演和多镜头剪辑；从单镜头到多镜头平均显著掉分。其电影语言三轴为指令遵循、时间连续、审美质量，覆盖镜头尺度、运动、角度、构图、焦点、色调、表演、场景、声音、剪辑和跨镜连续。[FilmBench](https://arxiv.org/html/2607.24241v2)

DirectorBench 进一步显示，工作流共同低分项常出现在镜头单元之间，说明评测和修复的主要对象应是转场、空间、人物状态、声音和节奏的跨镜关系，而非孤立帧。[DirectorBench](https://arxiv.org/abs/2605.30090)

MAST 对多 Agent 系统的研究提醒我们，增加角色常造成规范不完整、Agent 间错位、验证和终止失败。因此角色之间必须交换结构化产物与可验证回执，不能依赖自由对话或多数投票。[Why Do Multi-Agent LLM Systems Fail?](https://arxiv.org/abs/2503.13657)

## 直接竞品的实际成熟度

OpenDirector 自述九个 Agent 从一句话到完整视频。源码检查发现其图使用内存检查点，主要媒体任务是图像、TTS 与 BGM，主流程更接近静态分镜视频；它适合参考可视化图和流式交互，不足以作为真实多镜头视频与持久恢复的实现基线。[OpenDirector](https://github.com/seme-org/open-director)

Butterfly Director AI 的架构文档定义 11 个 Agent、Celery、Postgres、Redis 和 GPU 队列，但当前实际 LangGraph 主图只串联故事、人物和决策三个角色，其余多为分开调用。它说明“完整架构图”与“可运行端到端图”必须在报告中分开。[Butterfly Director AI](https://github.com/abhijha8287/butterfly-director-ai)

MovieAgent、FilmAgent 与 ViMax 提供了重要研究结构，但前两者安装与资源准备较重，ViMax 的公开活动有限。现有项目在不可变版本、恢复、授权、真实媒体检查和导出方面有更强的已实现证据。差异化不应是“角色更多”，应是“完整片真的生成、跨镜问题能定位和修复、过程可恢复和复现”。

## 产品候选

### 一句话承诺

输入一句关于未来的设想，电影导演 Agent 在可追溯、可恢复、可定向修复的制作流程中，交付一部 60–90 秒、有完整声画、可继续编辑的原创科幻短片。

### 第一用户与任务

第一用户是有故事构想、懂基本审美但没有完整剧组和模型工程能力的独立创作者。第一任务不是批量做社交素材，而是在固定时间和预算内，把一句高概念科幻设想变成一条叙事完整、声画统一、可以公开展示的微电影。

### 科幻导演知识与测试用例

本轮目标成片时长为 60–90 秒。单主角、单空间、单异常只保留为一个低复杂度测试用例，不能成为产品验收的全部依据。原先捆绑的 8–10 镜、16:9、少对白等均回到候选状态。多人互动、多场景、多个科幻设定、不同叙事与表演形式需继续讨论，既不默认排除，也不宣称已支持。版权与声音/肖像授权边界继续保留。

日常基线、异常出现、验证失败、选择或拒绝、后果显现、余波画面，是上述基础测试用例的一种可选叙事方法，不是通用故事合同或默认六阶段剧本。

镜头语法卡围绕叙事功能选择：空间建立、孤独/尺度、异常道具特写、主观怀疑、选择时的表演保持、后果揭示、首尾构图回声。每张卡包含叙事责任、推荐景别、视角、构图、允许动作复杂度、声音层和避免事项。卡不携带现成画面皮肤。

声音语法采用场景、镜头、镜内三个时间尺度的候选表示。环境声异化、空间感、声学母题和留白是可选方法，不能固定全部科幻影片的风格。BFI 强调声音对低预算科幻的作用，Sundance 建议配乐服务叙事。[BFI 科幻资料](https://www.bfi.org.uk/bfi-distribution/bfi-international-distribution/touring-programmes/sci-fi-days-fear-wonder) · [Sundance 短片建议](https://www.sundance.org/blogs/pep-talks-and-advice-for-makers-of-short-films-from-our-sundance-programmers/)

### 默认体验

1. 用户输入一句话，可选目标时长；默认自动完成，不设强制中途确认。
2. 制片统筹把一句话编译为故事蓝图和硬边界。
3. 视觉导演建立人物、空间、道具和色调的视觉圣经及镜头计划。
4. 生成制片并行产生镜头，关键镜头保留两个候选，普通镜头只生成一个。
5. 连戏监督检查每镜与相邻镜，失败只回退到受影响的最小阶段。
6. 剪辑与声音导演形成粗剪，整片审片后调整顺序、时长、声音和必要镜头。
7. 最终交付 MP4、字幕、制作台账、镜头/模型/许可回执和可选 OTIO/项目包。

用户能查看运行图、每个角色的产物、失败和修复，但默认界面仍是提示词、播放器和进度。Agent 内部讨论不作为产品价值展示；可验证产物和修复前后结果才展示。

## 多 Agent 设计

建议六个有真实职责的 Agent：

1. 故事导演：根据创作意图组织人物与关系、世界规则、事件和叙事结构，不强制单一异常或反转。
2. 视觉导演：创建多实体视觉圣经、场景状态和镜头语言；具体模型限制由生成计划处理，不覆盖故事范围。
3. 生成制片：把镜头计划编译为具体模型请求、参考包、预算和并发计划；本身不自由改故事。
4. 连戏监督：比较人物、空间、道具、光色、动作起止和相邻镜头，给出局部可执行修复指令。
5. 剪辑声音导演：形成粗剪、画面锁定、场景/镜头/镜内声音计划和混音。
6. 观众审片：从目标观众和电影级检查点审阅整片，只能提出带时间范围和证据的修复请求。

中央运行图是确定性调度器，不伪装成第七个会聊天的角色。Agent 输出必须通过严格 Schema；模型没有直接写数据库、改版本或执行任意 Shell 的权限。生成、下载、探测、转码、混音和发布候选都由类型化工具执行。

回路有明确预算：故事/镜头合同最多修订两轮；普通生成镜头最多一次模型自修复，关键镜头最多两次；粗剪整片最多一次结构回退；技术 QC 可重复到通过或明确失败。耗尽预算后输出可诊断失败，不进入无限反思。

## 技术候选

### 模型与媒体

MiniMax H3 API 适合作为竞赛主视频后端：支持 4–15 秒、768P/2K、文本、首尾帧或多参考图/视频/音频，并返回异步任务状态；原生生成立体声。H3 的开源权重不包含托管的 Context-IR 完整工作流，主路径应把我们的镜头/参考编译器作为可展示能力，不能只调用 Context-IR 后把结果包装成 Agent。[H3 API](https://platform.minimax.io/docs/api-reference/video-generation-v2-create) · [H3 开源说明](https://www.minimax.io/news/minimax-h3-open-source)

Wan2.2 TI2V-5B 支持 720P/24fps、约 24GB 显存和 Apache-2.0，可在 DGX/4090 类设备做开放回退。14B 路径约需 80GB，首发不默认使用。[Wan2.2](https://github.com/Wan-Video/Wan2.2)

HunyuanVideo 1.5 最低约 14GB、支持 T2V/I2V 和训练，适合作为第二技术探针；LTX-2.5 原生多镜头和同步音频很有吸引力，但要求 32GB+、版本与许可很新，不进入竞赛首发。[HunyuanVideo 1.5](https://github.com/Tencent-Hunyuan/HunyuanVideo-1.5) · [LTX-2.5](https://docs.ltx.io/open-source-model/getting-started/overview)

视觉锚点首选 Qwen-Image-Edit-2511 或 H3 多参考输入；研究和模型卡均支持“先建立视觉锚点再生成镜头”的路线。声音优先采用无正面对口型的旁白：CosyVoice 3 可提供中文/英文、情绪和语速控制；ACE-Step 1.5 可生成场景级音乐。采用时锁定具体模型、权重和许可文件，不把项目页宣传等同于法律审查。[Qwen Image Edit](https://huggingface.co/Qwen/Qwen-Image-Edit-2511) · [CosyVoice](https://github.com/FunAudioLLM/CosyVoice) · [ACE-Step 1.5](https://ace-step.github.io/ACE-Step-1.5/)

### 成本候选

按 2026-09-04 H3 公开价，768P 为 0.08 美元/生成秒。75 秒基础素材约 6 美元；仅对 30% 时长定向重生约增加 1.8 美元；全部保留镜头升级 2K 约再增加 3.75 美元，视频部分约 11.55 美元。若所有镜头都生成双候选，基础成本会接近 12 美元且还未含重生。因此默认只给高风险镜头双候选，并把每次生成秒数和费用冻结到运行台账。[MiniMax 定价](https://platform.minimax.io/docs/guides/pricing-paygo)

### 架构与部署

保留 TypeScript/React/Express 控制面。新建 `server/film-agent/`、`shared/film/` 和 `client/src/film/`，不继续膨胀 2813 行的 `runtime.ts` 和 3070 行的 `project-repository.ts`。新运行图通过端口适配已有 Blob、版本、指标、审查和导出服务。

魔搭创空间使用 Docker，监听 `0.0.0.0:7860`，SQLite 和媒体元数据放 `/mnt/workspace`；Provider 密钥使用 Studio Secrets。默认重启会丢非持久路径数据，最终视频从 Provider URL 成功返回后立即下载并校验到 Blob Store。公共 Studio 只调用类型化 HTTP 工具，不加载项目内 Pi 扩展或任意 Shell。[ModelScope Studio](https://modelscope.cn/skills/modelscope/modelscope-studio)

DGX Spark 是 ARM64、128GB 统一内存、CUDA 13，适合 ComfyUI/Wan/Hunyuan 本地 Worker；NVIDIA 已提供官方 ComfyUI 视频工作流。它仍需要对 FlashAttention、Triton、自定义算子和容器架构逐项验证，不能仅凭内存容量宣布 H3/Wan 全部可运行。[DGX Spark](https://docs.nvidia.com/dgx/dgx-spark/system-overview.html) · [NVIDIA ComfyUI Playbook](https://build.nvidia.com/spark)

OTIO 作为交付投影，不作为内部唯一真相源。它适合表达镜头顺序、时长、轨道、转场、标记与外部媒体引用，但不嵌入音视频，也不能完整表达 Remotion 自定义图形。内部 FilmManifest 编译为 Remotion/FFmpeg 成片，并可额外导出 OTIO。[OpenTimelineIO](https://opentimelineio.readthedocs.io/en/latest/)

### 评价与可观测性

每个 Agent 节点记录输入产物哈希、输出哈希、模型和 Provider、提示版本、开始结束时间、Token/费用、工具调用、重试原因、评估回执和下游决策。每次局部修复都绑定具体镜头、失败检查点和父版本。

自动评测分三层：媒体技术门禁；VBench/FilmOps 类镜头指标；故事、跨镜连续、声音和整片节奏检查点。FilmOps 可提供景别、构图、角度、色调、人物布局和镜头运动，但部分权重有额外许可且 GPU 较重；首发可先使用轻量算子和结构化 VLM 检查，最终结论仍需盲评。[FilmOps](https://github.com/Neo-yk/FilmOps)

原先按四个主题凑八条提示的评测方案需重做。候选矩阵交叉覆盖低复杂度基础用例、多人物互动、多场景衔接及不同科幻设定/叙事形式；数量、能力边界与保留集待确认。比较新系统、同后端单 Agent 与无审片回路版本，记录完整度、成本、叙事、人物/空间/状态、动作、声音及总体偏好。单一低复杂度用例不能证明通用性。

## 复用与重构决定

直接复用：Blob 与内容身份、不可变版本/分支、ProviderAttempt、恢复检查点、成本与事件台账、媒体探测、Remotion/FFmpeg、ReviewPacket、QC、项目包与 React 播放器。

通过适配器复用：现有 ProjectRepository、EditManifest、素材授权和本地 Pi 工作区。它们的概念可复用，但不让 `PrimaryVideo` 继续成为新项目的必填根。

冻结：v0.4 三模板推荐、模板确认门、固定 FirstCut 生产器、只看一个 before/after 静帧的审查合同、默认全语义口播保留逻辑。

## 主要风险与止损线

1. H3 质量或可用性未验证：9 月 7 日前若三镜头探针无法稳定产生可用素材，立即把生成层切到可访问的 API 组合，不继续押注本地部署。
2. 角色一致仍失败：先尝试参考、模型和局部修复；删角色、隐藏正脸或合并场景等会改变创作意图的降级需所有者同意。
3. 公共 Studio 无法完成重媒体渲染：Studio 只展示控制面和已完成案例，实时生成任务走外部 Provider；不得伪装成 Studio 本地生成。
4. 十天内 OTIO/FilmOps 过重：保留契约与接口，首发只交 MP4、SRT、Manifest、运行追踪；不把未验收能力写成完成。
5. 多 Agent 成本失控：每个节点固定输出 Schema、Token 上限、回路次数和停止原因；同一模型扮演多个角色也必须保留独立上下文与验收职责。
6. 公开版权风险：只用原创提示、生成素材、已许可音乐/字体/声音；保留模型和素材回执；作品显著标注 AI 生成。
