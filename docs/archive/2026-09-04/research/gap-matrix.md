# AI 电影 Agent 深度调研证据缺口矩阵

**日期：** 2026-09-04
**用途：** 产品方案与技术方案内部取证，不是已确认产品合同。

| 关键问题 | 已取得证据 | 判断 | 置信度 | 仍待实测 |
|---|---|---|---|---|
| 比赛真正奖励什么 | 官网动态规则给出电影 Agent 的五项评分：Harness 30、统一一句话生成 25、技术与模型工程 25、自主作品 10、复现开源部署 10 | 工程底座与端到端成片同等重要，只有工具演示不够 | 高 | 主办方是否提供隐藏测试提示词、测试时长与调用预算 |
| 当前项目能否直接参赛 | 仓库当前入口仍是上传视频、理解素材、确认模板后制作；代码把首版绑定到三套固定模板 | 不能直接满足一句话生成电影，需建立新的电影生成领域层 | 高 | 真实部署后现有 UI/Runtime 可承受的并发和媒体体积 |
| 是否需要彻底推倒重写 | 现有代码已具备持久项目、不可变版本、ProviderAttempt、恢复、审查包、渲染、QC、项目包和成本记录；核心运行时与仓库层已膨胀到 2.8k/3.0k 行 | 采用并行 v0.5 领域模型与编排层；保留成熟基础设施，冻结旧 v0.4 合同 | 高 | 新旧仓储复用是否需要薄适配器或抽取共用内核 |
| 多 Agent 是否天然优于单 Agent | FilmAgent、Hollywood Town、MAViS 显示角色化协作和有界反馈可改善结构/一致性；MAST 显示多 Agent 常见规范、错位、验证和终止失败 | 只建立有独立产物、工具和验收责任的角色；禁止自由聊天式“剧组表演” | 高 | 在同一模型与预算下，与单 Agent 基线的消融测试 |
| 影视生成的最大技术瓶颈 | FilmBench、DirectorBench、MAViS、FilMaster 均指出多镜头、跨镜过渡、人物/场景一致、动态表演、声音和节奏是主要瓶颈 | 质量闭环应围绕镜头间问题和整片节奏，而非单帧美观 | 高 | H3/Wan 在参赛故事上的真实失败分布 |
| 科幻电影 Agent 应覆盖什么 | 用户于 2026-09-04 接受 60–90 秒，明确否决单主角/空间/异常产品边界；原赛事选题建议只能作为方法参考 | 单主角/空间/异常仅是一个基础测试用例；多人、多场景与不同叙事/设定的能力范围继续讨论，不能提前宣称已支持 | 用户决定明确，实施能力待验证 | 确认多维测试矩阵、优先级和复杂度预算；重新评估原排期与模型推荐 |
| 哪个视频模型适合首发 | H3 API 支持 4–15 秒、768P/2K、最多 9 图/3 视频/3 音频参考并原生立体声；Wan2.2 5B 可在 24GB 显存运行 720P；HunyuanVideo 1.5 最低约 14GB；LTX-2.5 原生多镜头音视频但要求 32GB+ 且版本很新 | H3 API 作为竞赛主路径，Wan2.2 5B 作为开放本地回退；其余先做探针，不进入首发承诺 | 中高 | 三个代表镜头、每模型至少三种子的人评与成本/时延对比 |
| 角色一致性如何做 | Qwen-Image-Edit-2511 支持多图和人物一致编辑；研究显示缺少视觉锚点会使一致性显著下降；H3 支持多参考输入 | 先生成角色/空间/道具视觉圣经，再以锚点图驱动每镜头；不依赖文字描述维持身份 | 高 | 锚点数量、参考组合和漂移阈值 |
| 声音如何做 | FilMaster 将环境、音乐、VO、拟音、SFX 分为场景/镜头/镜内尺度；H3 原生音频，CosyVoice 与 ACE-Step 提供开放语音/音乐能力 | H3 原生声用于环境与动作，旁白由可控 TTS 生成，音乐单独生成/选择，最终分轨混音 | 中高 | H3 原生声能否稳定避免对白污染；人声与音乐实际可懂度 |
| 自动评价能否代替人评 | FilmBench 证明领域算子优于通用 MLLM；VBench 只覆盖通用视觉维度；DirectorBench 主张分检查点评价；现有仓库曾把技术 QC 误当审美通过 | 机器门禁用于淘汰与定位，人类整片盲评仍是发布/竞赛质量结论的依据 | 高 | FilmOps 在生成式科幻素材、中文提示和低样本上的迁移效果 |
| 魔搭创空间如何承载 | 官方资料支持 Gradio/Streamlit/Static/Docker；Docker 监听 7860；默认重启丢数据，持久目录 `/mnt/workspace`；xGPU 会按请求调度且有时长限制 | 公共 Studio 只做控制面、状态与轻量合成；重模型走 API 或独立 GPU Worker | 高 | Studio 的实际构建大小、请求超时、Chromium/Remotion 运行与外网回调 |
| DGX Spark 能承担什么 | 官方规格为 ARM64、128GB 统一内存、CUDA 13、Docker/NVIDIA Runtime；NVIDIA 已给出 ComfyUI + Wan/Hunyuan 视频工作流 | 适合作为本地生成 Worker 和开放模型证明，但 ARM64/CUDA 扩展需逐项移植验证 | 高 | Wan/H3/FilmOps/CosyVoice 所需 wheel 与自定义 CUDA 算子在 GB10 上的兼容性 |
| 开源提交如何处理 | 当前仓库私有，历史含大量研究/证据和本机边界；评分要求复现、开源、创空间部署 | 从私有主仓抽取可复现竞赛版公开镜像，避免直接公开历史仓库 | 高 | 主办方对“部分开源”与模型密钥/付费 Provider 的接受口径 |

## 停止条件

本矩阵记录的是取证状态，不是产品审批。用户校正证明原范围推断过窄；即使外部资料充足，产品范围仍需讨论，旧日程与模型排序也需按新矩阵复核。

下列结论已有一手资料或多源交叉支持，再扩展同类检索不太可能改变方案：比赛评分、现有项目结构、电影 Agent 核心阶段、多镜头质量瓶颈、Studio/DGX 部署边界、H3/Wan 能力与主要许可。仍不确定的部分均需要真实模型调用、硬件或主办方答疑，不能继续靠网页资料消除。
