# Movie Agent：集中体验反馈

状态：反馈和独立走查已汇总。2026-09-08 用户随后明确授权优先完善前端，结果见[本轮验收](./frontend-experience-2026-09-08.md)；创作判断和电影质量问题仍待后续处理。

本记录整理用户在本任务中的实际意见、追问及已核对的能力边界。以下走查记录保留当时范围：用户先要求人工体验和集中收集，由独立 GPT-6 Medium 任务中立走查，并授权最多 10 次、每次 10 秒以内的生成。当时尚未授权修复；随后前端授权单独记录在上述验收中，不改写原始走查结果。

## 用户明确报告的问题

| 编号 | 用户反馈 | 当前应如何理解 |
|---|---|---|
| U1 | “这个剧本，感觉非常的无聊，也没有体现什么价值，甚至我都看不懂。” | 已展示故事的吸引力、价值表达和可理解性未通过用户评价。上下文指向《回声频率》，精确所看版本未指定，不扩展为其他作品的评价。 |
| U2 | “现在的前端还没有运行的 Trace，感受不到 Agent 在运行。” | 用户缺少可感知的工作进展，不能只凭后台已有事件认定问题解决。 |
| U3 | “现在的整体UI非常僵硬，功能可以说跑通了。” | 交互自然程度和使用感受未达到用户预期。此前 UI 暂定通过不是永久验收；具体触发场景待独立走查补充。 |
| U4 | “效果我感觉不见得会比 Pi agent 或 codex 好。” | 用户对垂直产品的增量价值存疑。这是用户感受，尚没有同任务、同模型、同工具、同预算的直接对照，不写成已经证明优于或劣于这些产品。 |
| U5 | “托管模式的效果我觉得不太行，agent自己的判断力不足。” | 用户对自主创作、决策及推进能力不满意。需观察真实任务中的独立判断，不能由 Codex 给出详细修复步骤后算托管成功。 |

正面反馈也保留：用户此前认为“视觉效果蛮好的”，但该意见不等于全部资产、声音和连续性通过。用户已要求逐项人工核对所有生成资产，见[首轮人评记录](./human-review-2026-09-07.md)。

## 用户提出的能力透明度问题

这些是用户的追问和核对诉求，不自动归类为用户已经要求新增的功能：

- 哪些工作由 Movie Agent 完成，哪些由产品外的 Codex 操作、诊断或脚本完成。之前的整片制作有开发者纠偏；接口验证和声音对比部分由外部脚本直接调用底层模块。4319 资产审阅页是独立验收辅助页。
- 系统提示词如何设计：目前是共享创作原则和四类角色提示词；执行规则较细，创作有效性仍需作品证据。
- 是否有自动上下文压缩：已核对本地 AgentScope 的默认机制，应用尚未做电影专用压缩策略和长会话保真验证；前端没有对应可见性。
- 系统上下文大小：此前约 3,500 tokens 仅为主导演提示词与工具定义的字节估算，不含历史、项目数据和图片，不是 GLM 精确 token 数。
- 是否有 Skill 及渐进式披露：当前产品没有 Skill 加载系统；读取项目摘要与完整产物属于业务资料按需读取。没有 Skill 不直接证明产品差，也不是用户已指定的修复方案。
- Agent 分工和传递：主导演模型按需委派，专业任务独立上下文，数据库共享产物，收件箱返回结果；职责主要靠提示词区分，基础工具重叠。多 Agent 的稳定收益尚无充分对照证据。

## 中立走查要求

新任务独立开始，不继承本任务完整对话。先完成一轮正常用户流程并保存初始观察，再阅读本反馈对照，减少被现有结论引导。可以支持、部分支持或不支持既有怀疑，不为证明用户或开发者正确而选择证据。

主要通过 4318 正式产品界面，以新建的、明确标注中立走查的测试项目体验。允许为了完成测试在自己的测试项目中提交审核或托管授权，但必须注明测试操作者身份，不充当真实用户对旧作品的人评，不批准或改变用户既有项目。

生成额度是上限，不要求用完。审慎计数：新付费媒体生成提交合计不超过 10 次，失败、重试、备选和结果不明提交均占用额度；图片也计入。视频／音频请求时长不超过 10 秒，不支持可靠限时的声音接口本轮不新增调用。普通对话推理、只读检查及本地合成不算媒体生成次数，但合理节制。H3 768P，Seedance 2.0 Fast 720P，禁止自行升规格。先保证实际提交不会突破额度，不仅依赖给导演的一句提示；无法保证时只做不生成的走查并明确限制。记录请求时长与实际文件时长的可能偏差。

允许只读查看代码和日志解释复现问题，不修改产品代码、提示词、全局配置或用户已有项目，不在幕后修好再继续冒充原流程成功。可创建独立测试工具及本地证据，需注明哪些操作发生在产品外。任何隔离测试环境或调用限额保护应单独说明，不伪装成产品内置能力。不能绕过内容审核，结果不明不能盲目重发。

报告每项包含：用户目标、操作步骤、期望与实际、证据及版本身份、影响程度、复现或不确定性、是否新增发现。分别列用户已反馈问题、独立新发现、无法验证的项目、实际可用能力，以及产品外干预。不得将模型观察写成人类质量验收。Pi／Codex 的直接优劣对照如未做，明确标为未验证。

报告目标路径：`docs/validation/neutral-walkthrough-2026-09-08.md`；原始截图、回执、生成额度台账等保存在 Git 忽略的 `local-data/neutral-walkthrough-2026-09-08/`。结论交回后再讨论修复，不自动开始修改或生成整片。

| 合并问题 | 对应发现 | 证据边界 |

| 自主方案存在内部矛盾 | N6，对应 U5：同一提案既要求固定机位、无移动，又允许推近或插入中近景且声称不增加镜头 | 文字托管中有具体证据；未实拍，不能泛化为所有托管任务都会失败 |

N1、N2、N4、N5、N7、N8 是用户此前未明确提出的具体新发现；N3 为运行可见性反馈补充证据，N6 为托管判断反馈补充局部证据。走查也确认了改稿保存、提交快照、跨版本标注、明确历史采用、共创审核和限定文字托管推进的可用子项。
