## 2. 三个参考项目的证据边界

| 项目与已核对版本 | 可吸收部分 | 不能据此认定 |
|---|---|---|
| ViMax，05a4894 | 故事到分场与镜头规划、参考资产和生成衔接、模型选工具 | 原运行时已支持我们要求的实时插话、细粒度调度和完整版本保护 |
| AdCraft，08cf7e6 | 简洁用户产物、版本绑定、计划冲突处理、模型重新规划与程序校验 | 广告流程或固定阶段适合直接作为电影流程；所有能力都是独立 Agent |
| OpenMontage，cd9f3c1 | 制作技能、工具组织、状态记录、可见进展、视听方向讨论 | 宿主 Agent 编排等于没有程序规则，或阶段检查点已经实现实时任务控制 |

具体观察：

- ViMax 的已核对 Web 入口使用逐轮读取消息的方式，停止接口终止 Agent 进程；修改后按文件种类标记下游过时。它不是已验证的实时选择性调度方案。
- AdCraft 的引导阶段有程序控制；计划发生版本冲突后，在 Pi 模型路径可重新规划一次，再由代码检查操作等价性与是否可沿用确认。
- OpenMontage 依靠宿主编码助手执行制作指令，但代码仍校验阶段前置条件与调用方提供的批准标记，并保留历史。批准标记校验不等于独立识别人类授权。

源码链接与观察依据见[交互决定来源](../product/creative-interaction.md)。复用前需核对具体模块、依赖与权重的许可；吸收设计不等于直接复制代码。

## 3. 四角色试验基线

下面是待验证的责任划分，不是最终 Agent 清单。

| 试验角色 | 主要责任 | 需要评审的拆分点 |
|---|---|---|
| 导演编剧 | 意图、故事提案、分场剧本与叙事修改建议 | 用户对接、总调度与编剧是否由同一个 Agent 承担 |
| 视觉制作 | 视觉方向、参考资产、镜头规划、图像和视频生成组织 | 美术、镜头设计、生成执行是否需要独立上下文 |
| 后期导演 | 剪辑、字幕、配音、音乐、音效、动效和声画修改 | 声音是否有足够独立的判断任务需要拆出 |
| 媒体与连续性检查 | 对生成内容、跨镜关系与声画偏差提供证据和修复建议 | 独立检查能否减少遗漏，是否值得额外时延与上下文成本 |

图像生成、视频生成、字幕、混音等首先是必须具备的能力；只有出现独立决策、上下文或反馈责任时，才值得单独设置 Agent。不能按工具数量分配 Agent。

正式剧本评分不设为运行中的必经 Agent。可按需做一轮专项剧本审查，再交给用户。

以四角色为试验起点，允许按证据拆分或合并，并与同模型、同工具的单 Agent 基线比较。角色数量不设固定范围。首轮七组二十一个场景族已确认，具体输入与对照条件仍待准备。

## 4. 模型决策与程序执行

| 模型负责判断 | 程序需要可靠提供 |
|---|---|
| 理解新消息属于讨论、修改还是停止意图 | 接收消息，并在明确边界交给 Agent；明确停止操作可被执行 |
| 修改影响哪些故事、镜头和声音 | 稳定的产物身份、依赖引用、计划版本与任务状态 |
| 何时暂停、继续、复用或局部补拍 | 查询、提交、取消和恢复能力，以及真实执行结果 |
| 批量标注如何综合处理 | 原视频版本、时间点、原意见和提交关系的保存 |
| 是否要提出创作讨论 | 当前共创／托管授权与已批准产物的可靠记录 |
| 采用哪条生成路径、是否切换模型 | Provider 的实际能力、参数约束、失败信息和用量记录 |

不采用固定的“相关任务停、其他继续”业务规则。程序应防止过时任务结果覆盖新版本，但不据此自动删除所有旧素材或否定复用价值。

约 30 分钟和目标费用不作为硬停止条件。重试、账户限制、异常终止和并发的具体机制要在可靠性设计中定义，不借技术实现重新引入产品已撤回的费用门槛。

## 5. 需要支撑的产物与关系

这是建模范围，尚未冻结 Schema、数据库或消息协议。

| 对象 | 必须能表达的关系 |
|---|---|
| 项目与创作意图 | 原始用户要求、Agent 补充建议、当前授权范围 |
| 故事提案与正式剧本 | 文档版本、用户手改、被制作采用的版本 |
| 视觉方案与参考资产 | 人物／场景／道具身份及适用范围，允许按需生成 |
| 镜头计划与生成任务 | 镜头叙事意图、参考来源、使用的计划版本、实际调用和结果 |
| 媒体候选 | 图像／视频／音频及来源、失败或采用状态 |
| 剪辑与声音 | 片段位置、对白与音乐等实际可用音轨、字幕和效果关联 |
| 成片版本 | 采用的素材与方案、父版本、比较和恢复依据 |
| annotation | 视频版本、时间点、用户意见、同次提交的标注集合 |
| 修改方案 | 用户要求、模型解释、影响范围、复用或重做建议、授权及结果 |
| 运行记录 | 任务状态、停止或恢复结果、真实耗时与费用 |

人物、场景和状态需要集合及关系表达，不能隐含单主角、单空间或只检查相邻镜头。剪辑中的相邻关系与剧情上的时空连续关系应区分。

手动编辑、应用修改与生成任务是不同事件；自动保存不能被解释成自动重生成。

## 6. 声音与视频耦合

产品要求支持成片后修改台词、语气、声线，并允许必要的局部补拍。技术评审需验证：

- 哪些声音由独立生成器提供，哪些来自视频模型的混合音轨。
- 声音素材怎样与角色、对白、画面时间和版本关联。
- 独立换配乐时，怎样保留已认可的画面。
- 改台词或表演时，什么时候能独立改声音，什么时候需要处理口型或补拍。
- 局部补拍怎样保持人物、服装、空间和前后声音连续。
- 字幕和对白更改怎样对应当前使用的剧本与音频。

原生音视频可作为生成路径，但不能推断其音轨天然可分离。声画补拍的方案由模型判断，实际控制能力与质量需验证。

## 7. 框架评审应回答的问题

下一轮评审应给出具体取舍及证据，而不靠框架名称定案：

1. 长媒体任务期间，新消息何时被主 Agent 看见。
2. 如何查询、取消、恢复任务，并处理外部请求结果不明。
3. 如何绑定文档、标注、媒体与批准的版本，处理迟到结果。
4. 如何支持共创、托管及部分托管，并持续展示产物。
5. Agent 上下文、工具边界和运行状态由谁管理，如何避免多个组件各自维护冲突状态。
6. ViMax 哪些模块可直接改用，哪些必须替换；AdCraft、OpenMontage 吸收到哪一层。
7. 选择现成框架与自行实现的差额是什么，是否值得承担自研工作。

本节不提前指定消息必须在哪个工具调用后交付，也不指定数据库、并发数和重试次数。

## 8. 评测与真实验证待办

仅验证插话、委派和恢复的三个场景已被指出覆盖不足。[首轮验证矩阵](../validation/first-round-matrix.md)的七组二十一个场景族已获所有者确认，分批覆盖电影产品与架构风险。以下为验证层说明，证据类型和观察点以该矩阵为准，具体输入与调用安排在执行准备中细化；目前尚未执行。

Mock 的用途限定为接口、控制流程和异常路径验证。它不能证明模型理解意图、故事有趣、生成一致或成片质量。执行时沿用相应任务已有授权；超出授权范围的动作另行处理。

| 验证层 | 应解决的问题 |
|---|---|
| 真实 LLM 交互 | 模糊意图、剧本修改、批量标注、部分托管与冲突意见能否被正确理解 |
| 图像与视频探针 | 共享参考能否维护身份、关键动作与场景连续，备选模型是否有效 |
| 声音与补拍探针 | 独立换配乐、修改台词／声线、必要的口型与局部补拍能否成立 |
| 运行可靠性 | 用户插话和停止、迟到结果、重复提交、进程恢复和版本保护 |
| 完整影片 | 90–120 秒故事与声画是否完整；生成问题是否得到处理 |
| 用户修改体验 | 单条／批量 annotation、改稿后明确应用、局部修复、版本比较与恢复 |
| 离线剧本与整片人评 | 故事是否有趣、表达是否成立；自动媒体检查与人评判断是否一致 |
| 架构对照 | 独立 Agent 的实际收益，以及额外时延、费用和失败成本 |

测试输入要覆盖不同人物、场景和叙事任务，单一低复杂度故事通过不能证明全部能力。用例、保留集、人数、指标与判定标准尚未冻结；本文件不制造得分阈值。

评测记录实际生成、返工与总用量，区分系统执行时间和用户审核等待，说明统计口径。30 分钟与费用目标不作为已达成指标。
